## 1. 为什么需要单独立卡

`internal/control/publicapi/empty.go` 里有一条明确的技术判断：V1.0 没有 `t_integration` / `t_tool` 表，`/api/public/integration-links` 与 `/api/v1/integrations/import-credentials` 因此**故意返回空 / 404**，并注明「把 `t_channel` 当公开接入点会泄漏拓扑」。

而 PRD F4-2/F4-3 要求：
- F4-3：深链模板**由后端持有**，运营可改参数名，前端不得硬编码（现有前端 `deepLink.ts` 已按模板渲染，但模板永远拿不到）；
- F4-2：一键导入按钮的安全断言已通过（Key 不泄漏进 DOM/URL/analytics），但**正向导入流程没有服务端**。

两件事都要新增存储与端点，属于**功能开发**，不是缺陷修复，因此单独立卡并要求先定范围。

## 3. 决策（D-30，2026-10-29 需求方已定稿，本卡内不再重议）

| # | 决策 | 结论 |
| :--- | :--- | :--- |
| Q1 | `POST /api/v1/integrations/import-credentials` | **不做**。V1.0 只做深链模板，导入由用户手工复制。该端点继续返回 404，并在 PRD/OI 标注「V1.0 不实现」。理由：PRD 未定义第三方导入协议，做了等于平台代收用户上游 Key，新增安全面。 |
| Q2 | 模板变量模型 | 只允许白名单占位符 `{key}` / `{base_url}` / `{model}`，服务端校验；出现其它占位符即拒绝保存。 |
| Q3 | 工具数量 | 固定 5 个（PRD §4.5），运营只能改开关与模板，不能增删。 |

以下为定稿前的三个决策点，保留以备追溯：

| # | 决策 | 选项 | 我的建议 |

## 4. 推荐方案（Q1=②、Q2=①、Q3=①）

| 层 | 内容 |
| :--- | :--- |
| 迁移 `0026` | 新表 `t_integration`：`tool_key`（唯一）、`display_name`、`enabled`、`deep_link_template`、`created_at/updated_at`；不含任何凭据字段 |
| 运营端点 | `GET /api/admin/integrations`、`PATCH /api/admin/integrations/{tool_key}`（改 `enabled` / `deep_link_template`），写审计；模板必须通过「只含白名单占位符」校验 |
| 公开端点 | `GET /api/public/integration-links` 返回**已启用**的 5 条（`enabled=false` 的返回 `deep_link_template: null`，前端已有兜底） |
| 运营页面 | `Page.adminIntegrations`（或并入现有设置页）：5 行表格，改开关与模板，保存二次确认 |
| 明确不做 | `import-credentials` 端点保持 404，并在 PRD/OI 里标注为「V1.0 不实现，手工复制」 |

## 5. 硬约束（若开工）

1. 模板渲染只允许白名单占位符，**必须**服务端校验；前端不得把 Key 拼进 URL（现状已保证，不得回退）。
2. 公开端点**不得**返回任何凭据、渠道 base_url、内部拓扑。
3. 新表必须带迁移 `down`，并更新 `scripts/check-eol.sh` 的 SQL 清单与迁移 checksum。
4. 不改 `/v1/*` 交易契约。
5. `bash scripts/check-eol.sh`、`TSC_OK`、`vitest`、`go test ./internal/control/...` 全绿。
