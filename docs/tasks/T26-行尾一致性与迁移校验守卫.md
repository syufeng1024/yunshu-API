## 1. 目标

给「字节被校验的文件」加一道**秒级、报错即给修复命令**的守卫，并把 Windows 旧工作区的行尾规范化步骤写进开发文档。目的是让下面这类故障在提交前就暴露，而不是等到 `migrate up` 时才炸：

```
迁移 0001 的 checksum 不匹配：库中 55b0b46…，文件 78273f6…
```

本卡**不改任何业务代码**，也**不改 checksum 算法**。

## 2. 故障实例（2026-10-28 实测，T25 验收时发生）

| 事实 | 证据 |
| :--- | :--- |
| `78273f6…` 是同一文件 **CRLF 版**的 SHA-256 | `sed 's/$/\r/' 0001_account_credential.sql \| sha256sum` 可复现 |
| checksum 取文件精确字节、不做归一 | `internal/platform/migrate/load.go:125` `Checksum()` 是纯 `sha256.Sum256` |
| SQL 被编译进二进制 | `internal/platform/migrate/load.go:28` `//go:embed sql/mysql/*.sql` |
| 镜像打的是**构建时工作区字节** | `deploy/Dockerfile.app:37` `COPY internal ./internal` |
| 仓库规则已覆盖 SQL 与 golden，**未覆盖 Lua** | `.gitattributes` 仅两条：`sql/mysql/*.sql`、`checksums.golden` |
| 已有测试能抓 embed↔golden 不一致，但只在 `go test` 时 | `internal/platform/migrate/golden_test.go` 逐条比对 `Checksum()`，**不做行尾归一** |

**根因**：`.gitattributes` 的 `eol=lf` 是 2026-10-28 才随 pull 进仓库的，**已存在的旧工作区不会因此自动 renormalize**；该机器上的 SQL 仍是 CRLF，于是 build 出的镜像内嵌 CRLF，与库中记录的 LF 版本永久不匹配。

**影响**：Windows 构建的镜像与 CI（Linux）构建的镜像，同一份代码产生不同 checksum，数据库无法互换。这是上线阻塞点。

## 3. 必须先读准的三件事（避免做错方向）

1. **工作区大面积 CRLF 是正常态，不要去"修"它。** `core.autocrlf=true` 下 checkout 本来就把 LF 转 CRLF，实测 595 个已跟踪文件里有 467 个是 CRLF（含 360 个 `.go`）。**禁止做全仓 `git add --renormalize .`** —— 那会把 400+ 文件塞进一次 diff，且与 autocrlf 的预期行为冲突。
2. **只有"字节被校验或被编译进产物"的文件才需要 LF 钉死**。当前是：`internal/platform/migrate/sql/mysql/*.sql`（46 个）、`internal/platform/migrate/checksums.golden`。Lua 脚本（6 个，`internal/{breaker,idemstore,lock,ratelimit}/scripts/*.lua`）也被 embed，但**不参与任何 checksum 校验**，Lua 引擎容忍 `\r`，属"可加固非必须"。
3. **`golden_test.go` 已经存在且有效**，本卡是补它覆盖不到的那一段（构建上下文/工作区），不是重写它。

## 5. 硬约束（违反即打回）

1. **`check-eol.sh` 必须零依赖**：只用 bash + `tr`/`wc`/`grep` 这类 POSIX 工具，不得依赖 Go、Python、node。理由与 `lint.sh:5-7` 一致——`scripts/dev.sh ci` 要在只有 Go 的机器上可跑。
2. **禁止使用 `xargs` 批量传路径**。本机实测 `xargs: environment is too large for exec`，会让检查**静默返回空结果（假阴性）**。必须用 `while IFS= read -r` 循环。这条是本卡最重要的一条，写错等于守卫失效。
3. **失败信息必须可直接复制执行**，至少包含：
   - 命中文件列表（逐个列，不要只说"有 N 个"）
   - 修复命令：`git checkout -- internal/platform/migrate/sql/` 或 `git add --renormalize <path>`
   - 一句话说明后果（"会导致 migrate checksum 不匹配，镜像与 CI 产物不兼容"）
4. **禁止全仓 renormalize**（见 §3 第 1 条）。只允许对 §4 第 4 项列出的 6 个 Lua 和守卫清单内的路径操作。
5. **不得修改 `internal/platform/migrate/load.go` 的 `Checksum()`**，也不得在比对时对 `\r\n` 做归一。理由：那会削弱「已应用迁移不得修改」这条硬约束的强度，属于用降低正确性换便利。
6. **`check-eol.sh` 正常态必须 `exit 0` 且无输出**（不要打印"检查通过"之类的噪音，`lint.sh` 的风格是命中才说话）。
7. **必须在 `scripts/lint.sh` 里能被 `scripts/dev.sh ci` 与 CI `static` job 同时触达**（`static` job 已执行 `scripts/lint.sh`，无需改 `.github/workflows/ci.yml`；改动 yml 属越界）。
8. **文件域边界**：只碰 §4 的 6 项。禁止碰 `internal/**` 业务代码、`deploy/**`、`.github/**`、`web/**`。

## 6. 自检命令（逐条跑通，输出贴进回执）

```bash
# 1. 正常态：零输出、退出码 0
bash scripts/check-eol.sh; echo "EXIT=$?"

# 2. 负向验证：故意把一个 SQL 转成 CRLF，守卫必须报错并给出修复命令
cp internal/platform/migrate/sql/mysql/0001_account_credential.sql /tmp/bak.sql
sed -i 's/$/\r/' internal/platform/migrate/sql/mysql/0001_account_credential.sql
bash scripts/check-eol.sh; echo "EXIT=$?（期望 1，且输出含文件名与修复命令）"
cp /tmp/bak.sql internal/platform/migrate/sql/mysql/0001_account_credential.sql
bash scripts/check-eol.sh; echo "EXIT=$?（期望回到 0）"

# 3. 接入生效：lint 整体仍绿
bash scripts/lint.sh; echo "LINT_EXIT=$?"

# 4. Lua 已归一且规则生效
git check-attr eol internal/lock/scripts/renew.lua   # 期望 eol: lf
for f in internal/*/scripts/*.lua; do a=$(wc -c < "$f"); b=$(tr -d '\r' < "$f" | wc -c); [ "$a" -eq "$b" ] || echo "仍为 CRLF: $f"; done

# 5. checksums 未被误动（本卡不应改任何 checksum 值）
git diff --stat internal/platform/migrate/checksums.golden   # 期望空
```

### 10.3 额外的实测发现

1. **HEAD 里 46 个 SQL 全是纯 LF**（逐个 `git cat-file -p HEAD:…` 比对字节，CRLF 数量为 0）。说明仓库侧一直是干净的，历史故障纯由**旧工作区未 renormalize** 造成——本卡的诊断方向正确。
2. Windows 上 `touch` + `git checkout-index` 之后，`git status` 会对某个文件残留一个**假 M**（`git diff` 与 `git diff --cached` 均空、字节与 HEAD 完全一致）。这是 stat 缓存假象，`git checkout -- <file>` 即清。已记录，避免后续验收误判为"有未提交改动"。
3. Lua 归一后 `git status` 不显示改动——因为归一化后与索引内容一致，属正确表现，不是"没做事"。

### 10.4 遗留（不在本卡范围）

1. `release.yml` 构建镜像后**未校验**镜像内 embed 的 checksum 是否等于 `checksums.golden`（§8 第 2 条已裁定本卡不做）。这是本卡闭合后仍存在的最后一环：本地与 CI 的**工作区**现在都被守住了，但**镜像产物**还没被验证。建议后续单独立项，在 CI 内构建镜像后跑一次 `migrate -dry-run` 或直接 `go test ./internal/platform/migrate/` 于镜像内。
2. 旧工作区的 `git add --renormalize .` 仍需开发者各机手动执行一次；守卫会在执行前就报错并给命令，属可接受的人工步骤。
