## 5. 硬约束（违反即打回）

1. **表结构必须逐列满足读取端**（`body.go:44` 的列检查是硬门槛，缺一列整功能 404）：

```sql
CREATE TABLE t_request_body (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  request_id  CHAR(26)        NOT NULL COMMENT 'ULID，与 t_usage_record.request_id 同值',
  user_id     BIGINT UNSIGNED NOT NULL,
  ciphertext  MEDIUMBLOB      NOT NULL COMMENT 'AES-256-GCM 信封密文，绝不存明文',
  body_key_id VARCHAR(32)     NOT NULL COMMENT '正文独立密钥标识，不得为空',
  created_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  expires_at  DATETIME(3)     NOT NULL COMMENT 'created_at + log.retention_days',
  PRIMARY KEY (id),
  UNIQUE KEY uk_rb_request_user (request_id, user_id),
  KEY idx_rb_expire (expires_at),
  KEY idx_rb_user_created (user_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_as_cs;
```

   `uk_rb_request_user` 的列顺序必须与 `body.go:58` 的 `WHERE request_id = ? AND user_id = ?` 一致。collation 必须与既有表一致（`utf8mb4_0900_as_cs`）。

2. **绝不进网关热路径**。正文入队只能发生在请求**结束后**的异步写入环节（`usagewriter.go:138` 那个入口或其并列入口）。禁止在 `p01`–`p14` 任何 stage 内做 DB/加密封装。理由：正文上限 10MB，`Seal` 是 CPU 活，塞进 P02–P14 会直接拖慢流式首字节（TA-1.2 要求 30s 首字节）。

3. **密钥必须独立**。`body_key_id` 不得复用 `CHANNEL_KEY_KEK`。新增 `LOG_BODY_KEK` 环境变量（base64 32 字节）。若为此扩展 `cryptobox` 支持自定义 AAD/用途，**必须保证 Channel 上游密钥的既有行为与全部既有测试不变**；AAD 必须能区分两类用途，禁止让正文密文与上游密钥密文互换可用。

4. **开关语义是硬承诺**：`log.body_mode = meta_only` 时，`SELECT COUNT(*) FROM t_request_body WHERE user_id = ?` 必须为 **0**。不是「有行但列为空」。此条必须有一个直接断言它的测试。

5. **正文写入失败绝不影响请求与账务**。队列满 / 加密失败 / DB 错误 → 丢弃正文 + 打 `log_body_dropped{reason}`，`t_usage_record` 照常写入。参照 `usagewriter.go:20` 对 usage 队列 `drop()` 的既有做法。

6. **解密失败一律 404**，与 `body.go:69` 对空密文的处理保持一致。不得返回 500，不得返回空串伪装成成功。`log_body_open_failed` 打点便于区分「没开日志」与「密钥轮换丢了旧 key」。

7. **清理按 `expires_at`**：把 `purge_log.go:84` 的 `purgeCreated("t_request_body", bodyCutoff)` 改为按 `expires_at < now` 删，单批上限调到 **10,000**（TDS 4873）。同时保留 `created_at` 作为兜底条件防止时钟回拨导致永不过期。`t_usage_record` 的清理口径**不动**。

8. **迁移编号不得顺延**。必须用空缺的 `0022`，不许改成 `0026`。`checksums.golden` 用仓库脚本重生，禁止手填哈希。

9. **不得删除或放宽任何既有断言**。`guard_test.go` / `migrate_test.go` 只允许「计数同步 + 新表名入列」，diff 里出现被删的断言行即打回（这是 T24 段 2 已明确的口径）。

10. **文件域边界**：本卡只碰 §4 列出的路径。禁止改 `internal/control/logq/service.go` 的 HTTP 契约、禁止改 `api/openapi.yaml` 的现有响应结构、禁止碰 `web/`。

### 11.6 验收时发现的构建级问题（**非本卡引入，建议单独立项**）

在真实全栈环境应用 0022 时，`migrate` 报错：

```
迁移 0001 的 checksum 不匹配：库中 55b0b46…，文件 78273f6…
```

实测 `78273f6…` 正好是同一文件 **CRLF 版本**的 SHA-256（`sed 's/$/\r/' | sha256sum` 可复现）。链路是：

- `load.go:29` 用 `//go:embed sql/mysql/*.sql` 把 SQL 编进二进制，checksum 取文件精确字节（`load.go:125`，纯 `sha256`，不做行尾归一）；
- `deploy/Dockerfile.app:37` `COPY internal ./internal` 把**构建时工作区的字节**打进镜像；
- 仓库虽有 `.gitattributes` 声明 `eol=lf`，但**已存在的旧工作区不会因新增规则自动 renormalize** → 该机器上 SQL 仍是 CRLF → 镜像内嵌 CRLF，而数据库记录的是 LF 版本。

**影响**：Windows 上构建的镜像与 CI（Linux）构建的镜像，同一份代码产生**不同的迁移 checksum**，数据库无法互换，迁移直接拒绝启动。这是上线期的实质阻塞点，不只是本地环境问题。

**本次处理**：`git checkout -- internal/platform/migrate/sql/` 让 44 个文件按 `.gitattributes` 重新规范化为 LF，重建镜像后 `migrate` 退出码 0、`t_request_body` 已建、`schema_migrations` 含 0022（业务表 59）。

**建议**（待新卡）：
1. `docs/dev-setup.md` 增加一次性 `git add --renormalize .` 的说明，供已有旧工作区的开发者执行；
2. 在 CI 增加一条守卫：构建镜像后校验 `migrate` 内嵌 SQL 的 checksum 与 `checksums.golden` 一致，防止此类漂移再次漏过；
3. 可选：`migrate` 的 checksum 对 `\r\n` 做归一再比对 —— 但会削弱「已应用迁移不得修改」的严格性，需评估后再定。
