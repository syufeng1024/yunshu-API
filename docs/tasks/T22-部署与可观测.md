## 4. 硬约束（违反即驳回）

1. **`/healthz` 与 `/readyz` 语义分离**：`healthz` 只反映进程、**不探测依赖**；`readyz` 探测 Redis/MySQL/config。liveness 绑 `healthz`，readiness 绑 `readyz`。**不得**让 Redis 抖动触发 K8s 重启全部网关。
2. **灰度必须按 `Authorization` 哈希粘性分流**：用 `$http_authorization`，**不得**用 `$request_id`（每请求都变，等于随机分流，会让同一 Key 在灰度期被两个版本交替处理）。
3. **内部 SLO ≠ 对外 SLA**：99.5% 是内部目标，**任何对外页面/文档不得出现**；对外只写 PRD §9.2 的承诺项。
4. **降级必须可解释**：每种降级/拒绝都要有对应错误码与 `hint`（PRD §9.8）。不得出现"静默降级"——降级即返回可读错误。
5. **资金相关 fail-close**：余额镜像缺失 → 503；限流 Redis 不可用 → 503（除并发的节点内降级）。**不得**为"提高可用性"放行资金判定。
6. **优雅停机**：`drain_deadline` 120s，`preStop` + `terminationGracePeriodSeconds` 必须大于它。
7. **账本权限**：应用账号对 `t_ledger_entry` **无 `UPDATE`/`DELETE`** 权限；可用可选触发器双保险。
8. **备份含账本**，且**恢复后必须跑对账 8 断言**；未通过不得对外服务。
9. **密钥管理**：上游渠道 Key 与日志正文 AES-GCM 信封加密；KEK 在 KMS；**禁止**把密钥写进 ConfigMap/镜像层/仓库。
10. **日志不得含敏感值**（Key、密码、上行 `Authorization`、正文未脱敏）。
11. **许可合规**：`.go`/`.sql` 里 `grep -rn "QuantumNous"` 必须为空（这是"没把 AGPL 代码搬进来"的证据，不是署名门禁）。同时**不得**在页脚/关于页加 new-api 的署名 notice 或「基于 new-api」表述 —— 本项目未使用其代码，加了是**错误的来源声明**；参考其架构不需要署名，所以也不欠任何交代。若将来真要并入其代码（会让整体成为 AGPL 衍生作品），须先取得商务授权并改本节与 TDS §0。
12. **告警必须可执行**：每条告警规则附「看到它该做什么」的一行说明，并指向 runbook 章节。
13. **对账差异 > 0 为 P0 告警**，且必须阻断当日发布。
14. **CVE 扫描**：高危漏洞未修复不得发版（允许带例外清单 + 负责人 + 期限）。
15. **不得对外承诺延迟数字**（P99 60s 等是设计假设，不是 SLA）。

**两个字段本段没有数据源，按定数输出，不许自己发明**：
- `span_id`：输出空串。分布式 span 需要 otel，V1.0 不引入（与 D-02 一致）。
- `degrade_flags`：输出 `[]`（空数组，非 null）。真正的填充点见 §12.7 第 4 条。

**为什么不在网关出口输出请求级行**：出口时结算未完成，`in_tokens/credits_settled` 拿不到；而 `t_usage_record` 在失败路径也会写行（`Result=FAILED`，`FailStage` 记 P 号），所以 429/402 这类**预扣后**被拒的请求天然有行。代价是 **401/403/404 这类"预扣之前就被拒"的请求没有请求级日志行**——这是对 TDS「每条请求两行」的**偏离**，登记在 §12.7 第 1 条，理由：这类拒绝零成本、量大，逐条记日志等于给 DoS 送写放大；它们的可观测性由段 1 的 `gw_requests_total{err_code}` 指标 + 段 3 的 nginx access 日志覆盖。

### 13.4 偏离登记（接受，不返工）

1. **A10 的"UserAgent 塞凭据"改为塞 `model_requested`**：§12.2 的两张表都没有 `user_agent` 字段（TDS §5.1 有，但请求级日志取的是 usage 行，行里有 `user_agent` 列却没进日志 schema）。实现为 `Redact` 作用于**所有字符串字段**，测试用 `model_requested` 投毒，性质等价。要不要把 `user_agent` 加进 schema（会同时牵动 PII 边界）留给 T23 与隐私条款一起定。
2. **`FailStage` 有两种真实形态**：流水线写 P 号（`P05`/`P12`/`P08.5`），`dispatch.attribution()` 写 `ROUTE`/`UPSTREAM`/`CONVERT`/`SETTLE`/`CLIENT_ABORT`。`StageOf` 同时映射两套，未知值输出空串而不伪造阶段。卡面只说"别把 P 号写进 stage"，没覆盖第二种形态——接受现实现。
3. **枚举值未归一**：`usage_source` 输出库里的 `UPSTREAM_API`，`protocol_in/out` 输出 `OPENAI_COMPAT`，而 TDS §5.1 写的是小写 `upstream`/`openai`。日志消费端若要按 TDS 枚举聚合会落空。**登记 P2**（段 4 写告警规则时一并定，或在消费端做映射）。
4. **`ParseTraceparent` 比卡面更严**：要求小写 hex 且拒绝全零 trace-id，与既有 `httpsrv.traceIDFromHeaders` 对齐——否则同一请求的 `X-Trace-Id` 与新日志行会对"合法"给出两种结论。接受。
5. **`ts` 是 flush 时刻**：请求级行在异步批量 INSERT 成功后写出，最长滞后 ≈3s（`DefaultFlushInterval`）。请求完成时刻仍看 `t_usage_record.created_at`（同一 `created`）。接受，写进运维口径。
6. **`X-Request-Id` 清洗收紧**：>128 字节或含不可见字符（含空格）的客户端值，现在**生成新 id**；旧实现是截断/剥离控制字符后保留。属行为变化，但只影响畸形输入，且"不回声不安全值"更符合硬约束。接受。

### 13.5 遗留

1. **P1 · 无 traceparent 时仍是两个标识**：`X-Request-Id` = UUIDv7，`X-Trace-Id` = 其 sha256 派生 32hex，日志 `trace_id` = UUIDv7。TDS §5.2 要求"`trace_id` 与对外 `X-Request-Id` 同一值"。彻底统一要把 `NewRequestID` 改成 32hex，会牵动 idem 时间序、`t_usage_record.request_id` 宽度、审计与既有测试 → **不在日志卡里顺手改，交 T23 验收对照时连同 TDS §5.2 一并裁定**。
2. **P2 · 枚举值口径**（见 13.4 第 3 条）。
3. **P2 · `user_agent` 是否进日志**（见 13.4 第 1 条），与隐私条款一起定。
4. **未验证**：`-race`；日志采集端（本段只保证产出单行 JSON，采/索引/告警在段 4）；生产前置代理是否会改写/剥离 `traceparent`。
5. 段 1 的 P1（三进程共用 `GATEWAY_METRICS_ADDR`）仍未解，段 3 前必须定。
