## 2. 现状与根因（已核实，直接引用）

### G12

`internal/control/fund/plan_grant.go:161-168`：

```sql
UPDATE t_rate_limit_policy SET effective_to = ?, updated_at = ?
 WHERE scope_type = 'USER' AND scope_id = ?
   AND (effective_to IS NULL OR effective_to > ?)
```

条件是「结束时间还没到」，**没有限定 `effective_from <= now`**。于是：

- 一笔 `QUOTA_APPLY` 行 `effective_from = 次日 00:00`、`effective_to = +30 天`，`effective_to > now` 成立 → 被改成 `now`；
- 改完 `effective_to(now) < effective_from(次日)`，窗口**负长度**，行彻底失效；
- 用户在提额审批通过后买套餐，提额**静默消失**，没有任何审计与提示。

同时 `EffectiveQuotaApply`（`quota_apply.go:560-616`）写入提额行时**不会关闭**前序行，运行时按「`effective_from DESC, id DESC` 取第一条在效行」，所以未来行与 plan 行是**可以并存的**——修复不需要删未来的行。

### G11

`internal/control/fund/quota_apply_test.go:43` 的 stub 自行 `Incr cfg:ver`，`quota_apply_test.go` 里 `cfgVersion > 0` 的断言因此是**自证**。真实链路在 `internal/boot/route_snapshot.go:205`（`Publish`：`SET cfg:snap:ROUTING` → `INCR cfg:ver` → `PUBLISH cfg:invalidate`），由 `cmd/controld/main.go:153` 注入，本包测试没覆盖。

## 3. 决策（D-27，已由需求方确认，不在卡内重议）

1. **只关闭在效行**：`WHERE ... AND effective_from <= now AND (effective_to IS NULL OR effective_to > now)`。未来行（`effective_from > now`）**原样保留**，一个字段都不动。
2. **未来行的衔接靠窗口语义**：新 plan 行的 `effective_to` 保持 `NULL`（开放）。提额窗口开始后，因 `effective_from` 更新，提额行胜出；窗口结束后提额行不再在效，plan 行**自动恢复**。不要额外写「延迟任务」或「预约关闭」。
3. **在效提额行不得丢失额度**：买套餐时若命中一条 `source='QUOTA_APPLY'` 且在效未到期的行，截断原行到 `now`（保留审计痕迹），并补一条**续接行**：
   - `daily_quota_micro` = 原提额值（额度保留）；
   - `rpm` / `tpm` / `concurrency_quota` = **新购套餐**的三档（规格升级要生效）；
   - `effective_from` = 新 plan 行的 `from` **+1ms 起**（严格晚于 plan 行，保证「最新优先」读到续接行），撞 `uk_rlp_scope_active` 时逐毫秒重试（沿用现有最多 5 次的做法）；
   - `effective_to` = 原提额行的 `effective_to`（窗口不变）；
   - `source` 仍为 `QUOTA_APPLY`，便于审计区分。
4. **plan 规格取高语义不变**：`plan_grant` 的「取高不叠加 / 跨档覆盖 / 赠送到期日不动」必须保持，A8/A9 不得回归。
5. 不动表结构、不新增列、不加后台任务。
